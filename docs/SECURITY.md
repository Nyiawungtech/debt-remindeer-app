# Security model

- Supabase Auth owns passwords, email confirmation, sessions and TOTP. The client uses PKCE with persistent local browser storage, allowing email links in a new tab in the same browser and installed-app sessions. Sign-out clears the session and detaches this device’s push subscription. Production Auth requires confirmed email, at least 12 password characters and secure email changes.
- Every debt, installment, payment, reminder and profile is keyed to its owner. Composite foreign keys prevent linking another account’s records. Clients receive SELECT privileges under RLS; public API wrappers run as invoker and call narrow functions in the unexposed `duewell_private` schema. Every mutation checks ownership. RLS identity checks are cached once per statement.
- Verified TOTP factors require an AAL2 token for both database reads and mutations. This is enforced in PostgreSQL, not only in a hidden UI. Keep an account recovery process and Supabase administrator access: the app does not invent TOTP recovery codes.
- Money uses integer cents. The database validates schedule totals, positive amounts and dates. Payments lock the installment row and use a caller request UUID, preventing concurrent overpayment and duplicate retries. Reversals preserve history.
- This release permits email and Web Push. SMS is disabled through UI, RPC guards and profile/queue constraints. The dormant SMS callback does not authorize sending. Push endpoints are restricted to browser push providers in both PostgreSQL and the worker; clients cannot read subscription encryption keys or reassign another owner’s endpoint.
- Email destinations come from the confirmed Supabase account email, never from a debt form. Push destinations are registered by the signed-in owner after device permission. Email and push content omit debt names and amounts by default. Channel opt-out cancels pending jobs; the worker checks the preference again immediately before sending.
- The scheduler uses a random secret. Service-role access uses Supabase-injected modern keys. Active delivery credentials are encrypted in Vault and exposed only through a service-role-only API. Its allowlist excludes deferred SMS credentials; optional Edge environment settings take precedence.
- The worker rechecks channel eligibility, preference and remaining balance immediately before dispatch. A payment made in the short interval after that check and before a provider accepts a message may still race with delivery. Already accepted messages cannot be recalled.
- No exactly-once guarantee is claimed for network sends. Unknown results are marked uncertain rather than retried automatically. Status shows provider acceptance; no device or inbox delivery/read receipt is fabricated. Push prunes 404/410 devices and avoids replaying an entire job after any device accepted it. Resend requests use a stable per-reminder idempotency key.
- Only public static assets are cached by the service worker. Real debt data is fetched after authentication and is not persisted in an offline cache. The demo uses separate, in-memory sample records.
- User text is rendered as React text. No user content is interpreted as HTML. Static deployment headers restrict scripts, framing, API connections and sensitive browser features. Confirm the actual host applies them.
- Account deletion requires a server-validated session, current password and AAL2 if enrolled, then cascades tracked data. Provider logs/backups have their own retention and are not falsely claimed to be erased instantly.

Automated database tests run real PostgreSQL semantics through PGlite with test-only Auth schema stubs. They do not replace a deployed Supabase penetration test, provider policy review, dependency maintenance or an independent audit. No “unhackable”, bank-grade certification or production audit is claimed.

- Request authorization also checks that the user and session still exist. A logged-out access token cannot continue reading or mutating the tracker until its normal JWT expiry.
